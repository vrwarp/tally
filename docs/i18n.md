# Speaking three languages

Tally is used by a church whose families speak English, Mandarin and Cantonese.
The roster already carries their names in their own script — Planning Center
writes a child with a nickname as `Benson “蔡秉洲” Tsai`, and Tally has stored
that composite since the beginning. Every word around those names is English.

This document is the plan for changing that: **English, Simplified Chinese
(zh-Hans) and Traditional Chinese (zh-Hant)**, to the standard
[`vrwarp/numbers`](https://github.com/vrwarp/numbers) already holds — where a
missing translation is a red build rather than an English word on a Chinese
screen.

It is written to be executed in order. Each phase leaves the repo shippable.

---

## What we are copying, and what we are not

Numbers solved this once already, and the valuable part is not the library — it
is the **pipeline around the catalogue**: a record of which English each
translation was made from, a translator note per key, a drafting script that
respects human review, and a test that fails when English drifts ahead of the
Chinese. That machinery is framework-agnostic and ports almost verbatim.

The library does not port: Numbers is Next.js and resolves the locale on the
server. Tally is a static Vite SPA with two entry points and a Cloud Functions
backend.

The bridge is that **`next-intl` is a thin Next.js wrapper over `use-intl`**, by
the same author, with the same `useTranslations` API, the same ICU catalogue
format and the same typed-messages declaration. Tally takes `use-intl`
directly. Numbers' `scripts/translate-messages.ts`, `src/lib/translation-state.ts`
and `tests/unit/messages.test.ts` come across with the imports changed and
almost nothing else.

| Numbers | Tally | Ported? |
| --- | --- | --- |
| `next-intl` | `use-intl` | swapped |
| `src/i18n/request.ts` (cookie → `Accept-Language` → en) | `src/i18n/resolve.ts` (localStorage → `navigator.languages` → en) | rewritten, same shape |
| `messages/{en,zh-Hans,zh-Hant}.json` | same | same |
| `messages/translation-state.json` | same | verbatim |
| `messages/GLOSSARY.md` | same file, Tally's vocabulary | structure verbatim |
| `scripts/translate-messages.ts` | same | near-verbatim |
| `src/lib/translation-state.ts` | same | verbatim |
| `tests/unit/messages.test.ts` | `tests/messages.test.ts` | near-verbatim |
| `global.d.ts` typed messages | `src/types/messages.d.ts` | same idea |
| API errors → codes → `Errors.*` | `HttpsError` codes → `Errors.*` | same idea |

## The four rules

Lifted from Numbers' conventions, because they are what make the catalogue
survive contact with a second year of development.

1. **Every user-visible string comes from `messages/<locale>.json`.** Including
   placeholders, `title`, `aria-label`, toast text and confirm prompts.
   `en.json` is the only source of truth; the Chinese catalogues mirror its key
   set exactly.
2. **Whole sentences per key.** Never assembled from fragments. ICU plurals
   instead of `count === 1 ? 'name' : 'names'`. Each ternary branch is its own
   key. This is the rule that costs the most to follow and saves the most:
   Chinese has no verb agreement and different clause order, and a sentence
   stitched from three JSX children cannot be reordered by a translator.
3. **Every new key gets a `context` note.** Required for anything short or
   ambiguous — button labels, status chips, `Errors.*`. It is fed verbatim into
   the drafting prompt, so the translator never guesses at "Clock" or "Held".
4. **Never translate data.** Student and adult names, event titles a leader
   typed, label-template `{{tokens}}`, Material icon names
   (`local_fire_department`), grade values, backend ids.

## Phase 1 — Infrastructure

*Target: the loop works end-to-end on one screen. Nothing else changes.*

### 1.1 The locale module

`src/lib/locales.ts` — dependency-free and client-safe, imported by both entry
points and by the kiosk.

```ts
export const LOCALES = ['en', 'zh-Hans', 'zh-Hant'] as const;
export const DEFAULT_LOCALE: Locale = 'en';
export const LOCALE_LABELS = { en: 'English', 'zh-Hans': '简体中文', 'zh-Hant': '繁體中文' };
```

Script subtags rather than regions, for Numbers' reason: the Traditional-Chinese
audience spans Taiwan *and* Hong Kong. `negotiateLocale()` maps `zh-TW`,
`zh-HK`, `zh-MO` and `zh-Hant*` onto `zh-Hant`, every other `zh-*` onto
`zh-Hans`, and everything else onto English.

### 1.2 Resolution and persistence

Three storage tiers, because Tally has three kinds of reader:

| Reader | Where the choice lives | Why |
| --- | --- | --- |
| Counselor / core team | `users/{uid}.locale`, mirrored to `localStorage` | follows them to a new phone, like Numbers' `User.locale` |
| Signed-out visitor | `localStorage` only | there is no account to write to |
| Kiosk | `tally:kiosk:locale` in `localStorage` | the choice is a fact about *the tablet in this lobby*, not about a person |

`firestore.rules` currently lets a user touch exactly one field on their own
document:

```
allow update: if … (isSignedIn() && request.auth.uid == uid
                    && touchesOnly(['lastSeenAt']));
```

That becomes `touchesOnly(['lastSeenAt', 'locale'])`, with a rules test for both
the permitted write and the still-forbidden `role`/`active` escalation beside
it.

### 1.3 The provider

`IntlProvider` at both `createRoot` sites — `src/main.tsx` and
`src/kiosk/main.tsx`. The kiosk's is deliberately separate: it reads a different
storage key and a different catalogue slice (§4).

### 1.4 Typed keys

`src/types/messages.d.ts` declares `AppConfig['Messages'] = typeof en`, so a
typo'd `t('…')` fails `npm run build` rather than rendering a key path on a
screen. This is the single highest-value line in the whole plan.

### 1.5 The pipeline

Ported from Numbers:

- `src/lib/translationState.ts` — `flatten`/`unflatten`, `messageArguments`,
  and the two declared cross-key invariants (`SAME_VALUE_GROUPS`, `QUOTED_IN`).
- `scripts/translate-messages.ts` — drafts missing/stale keys in batches, pins
  `messages/GLOSSARY.md` into every prompt, validates that each draft preserves
  the English ICU arguments, and never overwrites a key a human marked
  `reviewed` without `--force`.
- `tests/messages.test.ts` — key parity, ICU-argument parity, no empty
  messages, both cross-key invariants in every locale, and source staleness.

One Tally-specific change: Numbers drafts through its own AI provider plumbing
(`src/lib/ai/providers`), which Tally has no equivalent of. Tally's script takes
an API key from the environment and is otherwise identical; `--todo` and
`--sync-state` work with no key at all, which is what CI and most contributors
need.

### 1.6 Test wrapper

90 test files import `render`/`renderHook` from `@testing-library/react`, each
behind its own local helper — 334 call sites. Rather than edit 334 helpers, add
`src/test/rtl.tsx`, which re-exports the whole of Testing Library with `render`
and `renderHook` wrapped in an `IntlProvider` pinned to `en`. A one-line codemod
rewrites the module specifier in all 90 files.

### 1.7 Proof

Extract one screen — Insights (`src/features/dashboard/DashboardPage.tsx`) — plus
the nav labels, run `npm run translate -- --todo`, then `npm test`.

**Done, and both gates were verified by deliberately breaking them:**

- Rewording `Dashboard.tileMia` in `en.json` from "MIA" to "Missing" turned the
  staleness test red, with both versions named in the failure:
  `translated from: "MIA" / en.json now: "Missing"`.
- Changing `Nav.insights` in `zh-Hant.json` turned the same-value test red:
  `Nav.insights must equal Dashboard.title (same UI element in two places)`.

45 keys, 3 catalogues, `translation-state.json` tracking all of them.

## Phase 2 — Extraction

*Target: `en.json` holds every user-visible string. Still English-only.*

Roughly **2,300 candidate strings across 109 files**. This is the long tail, and
it is safely interruptible: each screen is independent.

**The governing constraint is that extraction must be value-preserving.** Tally
has 1,162 unit-test text queries and 834 e2e ones against only 8
`data-testid`s. If every `en.json` value is byte-identical to the literal it
replaced, and tests run pinned to `en`, all 1,996 assertions keep passing
untouched. Deviating from the exact English is a separate, later commit.

Order, cheapest-risk first:

1. `src/components/ui` + `src/components` — shared chrome, ~70 strings.
2. `src/features/*` screen by screen — ~1,500 strings, the bulk.
3. `src/kiosk/*` — ~320 strings, under §4's constraints.
4. `src/lib`, `src/services`, `src/context`, `src/hooks` — ~410 strings, mostly
   error text and formatting helpers.

### One gotcha the first screen found

`useTranslations()` returns a new function identity per locale, so `t` has to
join the dependency array of every `useCallback`/`useMemo` that reads a string.
The Insights screen needed five. `react-hooks/exhaustive-deps` catches every one,
so it is noise rather than risk — but expect it on each screen, and add the dep
rather than silencing the rule.

### The sentence-assembly problem

~95 sites interleave prose with logic in a way English grammar leaks through:

```tsx
{listNames(held)} {held.length === 1 ? 'joins' : 'join'} this one:
`${list} ${names.length === 1 ? 'is' : 'are'} checked in. Welcome!`
{kin.length === 1 ? 'Another registration' : `${kin.length} other registrations`} in
```

Each becomes one key with an ICU plural:

```json
"heldJoin": "{count, plural, one {{names} joins this one:} other {{names} join this one:}}"
```

Chinese needs no plural branches — `other` alone is correct — which the drafting
prompt already states.

`joinNames()`'s `", "`/`" and "` becomes `Intl.ListFormat`, which gets `、` and
`和` right for free.

### Dates

8 bare `toLocale*` calls plus `date-fns format()` with hardcoded English
patterns (`'EEE, MMM d'`, `'h:mm a'`) across ~15 helpers in `src/lib/time.ts`.
A pattern string cannot produce `2月14日（週五）` or 上午/下午. These move to
`Intl.DateTimeFormat` via `useFormatter`, or to date-fns' `zhCN`/`zhTW`/`zhHK`
locale objects where the call site is not a component.

## Phase 3 — Server errors

*Target: the Cloud Functions stop speaking English at the user.*

72 `HttpsError` call sites in `functions/src` return prose that reaches the
screen verbatim. Numbers' answer is the one to copy: **the server emits a
machine-readable code; the client translates it.**

```ts
throw new HttpsError('permission-denied', 'Only an admin can do that.',
                     { code: 'auth.adminOnly' });
```

…resolved client-side by a `useCallableError()` hook against `Errors.*`, with
the raw English as the fallback for an unknown code. A code without a catalogue
entry fails the build, exactly as in Numbers.

### The shared-module carve-out

`src/lib/registrationFields.ts` is copied verbatim into the functions package by
`scripts/sync-functions-shared.mjs`, and it *imports nothing* — that is the price
of being shareable, and it is why its validation sentences are English literals
returned as data:

```ts
export type FieldCheck<T> = { ok: true; value: T } | { ok: false; error: string };
```

It cannot import an i18n runtime, and it must not. So `error: string` becomes
`code: ErrorCode` — a bare string union — and both callers (the kiosk's door
validator and the reviewer's form) translate at the edge. `tests/functionsShared.test.ts`
already fails on drift between the two copies, so this stays honest for free.

## Phase 4 — The kiosk

*Target: a lobby tablet speaks Chinese without breaking its byte budget or its
warm boot.*

`scripts/check-kiosk-budget.mjs` holds the tightest numbers in the repo: **250 kB
gzip** for everything reachable from `kiosk.html`, **130 kB** for the first-paint
subset. It already enforces two instances of one idea — *the kiosk is handed the
answers, not the code*:

- A gathering's theme is four hue names; `functions/src/kiosk/events.ts` runs the
  OKLCH gamut search and the chooser row carries **finished hex**.
- The icon catalogue is 60 kB of path data; the server looks one up and the row
  carries **one `iconPath`**.

i18n gets the same treatment, in three separate decisions.

### 4.1 Catalogue bytes — free, if fetched rather than imported

The budget script walks `.js` chunks: it reads the `assets/*.js` references out
of `dist/kiosk.html` and follows imports found in those chunks. A JSON catalogue
pulled with `fetch()` is **not in that graph at all**. A JSON `import()` is —
Vite compiles JSON to a JS module — so the distinction matters and is easy to get
wrong.

But the kiosk boots warm out of `localStorage` (`KIOSK_KEYS.roster`,
`participation`, `pulse`) precisely so a lobby screen is usable before the
network answers, and a blocking catalogue fetch would undo that. So:

- **Inline the `en` kiosk slice** into the bundle. It is the default and must
  paint on the first frame.
- **Fetch other locales lazily** and cache them under a new
  `tally:kiosk:messages` key. A kiosk switched to Chinese boots warm in Chinese
  from then on — the same move `src/kiosk/backdrop.ts` already makes with the
  Cache API.

### 4.2 The ICU runtime — precompile, don't ship a parser

**Measured in Phase 1: `use-intl` + `intl-messageformat` costs 15.2 kB gzip**
(total dist JS went 522.7 → 537.9 kB gz when the provider landed in the main
app). That is the one genuine cost, and it is charged whether the import is
static or dynamic.

The answer is to **compile messages at build time**, and the mechanism is
already in the installed package rather than something to build:
`use-intl/format-message/format-only` formats messages precompiled by
`icu-minify`, and — checked against `node_modules` — that module **imports
nothing at all** (1.9 kB minified, no `intl-messageformat`). The core reaches
its formatter through the bare specifier `use-intl/format-message`, so swapping
it is a **Vite resolve alias for the kiosk entry**, not a code change:

```
resolve: { alias: { 'use-intl/format-message': 'use-intl/format-message/format-only' } }
```

With the kiosk's ~320 strings precompiled, the kiosk carries the formatter and
not the grammar. Same trade as the palette and the icon: the expensive general
machinery runs where there is room for it.

Phase 1 leaves the kiosk at exactly the right starting line — its built chunk
graph is **byte-identical to before i18n existed** (same hashes, first paint
103.0 kB against a 127 kB budget). Nothing under `src/kiosk/` imports the
runtime yet, so Phase 4 begins from a clean measurement.

### 4.3 What the server should render — and what it should not

The chooser row already carries a resolved palette and a resolved icon. It
should also carry a **pre-formatted, localized date and time string**, which
deletes the date-formatting path from the kiosk as a bonus.

It should **not** carry the kiosk's UI strings. They are overwhelmingly static
chrome — the keyboard, the wizard, the confirm screen — and routing them through
`getKioskEvents` would mean the lobby screen cannot paint a word until a callable
answers. That breaks the warm boot, which is the thing that makes the kiosk
usable at all, and it turns every copy edit into a functions deploy.

### 4.4 A fourth budget assertion

The budget script has three guards and needs a fourth. One careless
`useTranslations` import inside `src/kiosk/` would re-add the ICU parser
silently — the exact failure mode the colour-maths and icon-catalogue guards
exist to catch. Assert the kiosk graph never reaches `intl-messageformat`,
matched on a string literal a minifier cannot rename, in the style of
`OKLAB_MATRIX` and `ICON_CATALOGUE`.

### 4.5 Language on the glass

A kiosk is used by parents, not by staff, and it is bound once and left alone.
So: the language is a **setup-time choice on the kiosk pairing screen** (staff
pick what this lobby speaks), plus a small persistent switcher on the search
screen for the family whose language is not the room's default. The switcher
must not be a modal — a parent mid-registration cannot lose their place.

## Phase 5 — Names in Chinese: pinyin search

*Target: a parent types `caibingzhou` and finds 蔡秉洲.*

The kiosk keyboard is one static QWERTY layout, and the kiosk **never focuses a
focusable element** — that is what lets it avoid the device's slow native
keyboard. So there is no IME, and a Chinese name is unreachable by typing it.
Pinyin is the answer, and it is nearly free because of how search already works.

`searchName` is a **stored, denormalized field** on `students/{id}`, built by
`buildSearchName(firstName, lastName)` and written by every ingest path
(`pco/mapping.ts`, `attendees32/mapping.ts`, `kiosk/registration.ts`,
`kiosk/amend.ts`, `services/students.ts`). The kiosk only reads it
(`kiosk/roster.ts`) and the matcher only matches over it (`kiosk/search.ts`).

So: **widen the haystack, not the kiosk.**

```
蔡秉洲  →  "蔡秉洲 caibingzhou cbz"
```

Full syllables *and* initials, so both `caibing` and `cbz` land. **No matcher
change at all**: `normalizeForSearch` already lowercases and folds diacritics,
and `compact()` already strips word gaps, so `caibing` matches `caibingzhou`
today.

### Where the table lives

Server-side, and nowhere else. `pinyin-pro` is ~944 kB unpacked (it handles
tones and heteronyms properly); `tiny-pinyin` is ~42 kB with no dependencies.
Either is fine in a Cloud Function and neither belongs in a bundle.

**The constraint to respect:** `buildSearchName` lives in the module set copied
into the functions package by `scripts/sync-functions-shared.mjs`, and
`tests/functionsShared.test.ts` fails if the copies drift. Putting a pinyin table
*inside* it would ship the table to the client and to the kiosk. So pinyin is a
**functions-only module that post-processes** `searchName`, never an edit to the
shared one.

Client-side writes (`services/students.ts`) write the CJK-only form; the existing
`onStudentCreated` trigger — or a companion `onDocumentWritten` — backfills the
pinyin. Same "handed the answers" pattern as the palette.

### Heteronyms

Surnames are where naive pinyin is wrong, and a roster is nothing but surnames:
單 is *shàn*, not *dān*; 曾 is *zēng*, not *céng*; 查 is *zhā*, not *chá*. A small
hand-curated surname override table sits in front of the library. This is the
one piece worth a human's attention.

### Two things it fixes for free

- **Sorting.** `Intl.Collator` on Hanzi orders by stroke or by pinyin depending
  on the locale. Sorting `sortByName` on the stored pinyin gives a stable A–Z a
  counselor can actually scan.
- **A backfill script** over the existing roster, in the style of
  `prune:occurrences` and `repair:chains`.

## Phase 6 — The icon picker

*Target: the event icon picker is searchable in Chinese.*

`searchEventIcons` matches a query against
`` `${label} ${name.replace(/_/g,' ')} ${keywords}` ``, over 115 icons. The two
halves of that haystack need opposite treatment.

**Labels are ordinary UI strings.** `EventIcons.<name>.label`, one `context` note
each, drafted like everything else. They are one or two words and genuinely
ambiguous — "Clock", "Groups", "Today" — which is exactly the case rule 3 exists
for.

**Keywords are a search index, not prose.** `'people group community crowd team
youth ministry congregation'` is a bag of words, and a bag of words is where a
drafting model does its worst work. So:

- **Keep the English keywords in the haystack unconditionally.** A
  Chinese-speaking leader may well type "camp". Nothing gets *worse* than today.
- Add a per-locale keyword bag, **hand-authored**, and build the haystack from
  `en.keywords + locale.keywords + label(locale) + label(en) + name`.
- **Run Phase 5's pinyin function over the Chinese bag at build time**, so 露營
  is reachable by typing `luying`. The picker is in the main app on a real
  keyboard, and a leader searching in Chinese otherwise has to switch IME
  mid-form.
- **Never translate `icon.name`** and never drop it from the haystack. It is the
  paste path — somebody arriving with `local_fire_department` from Material's own
  docs has to find the icon it names.

~230 keys per locale. Mark the keyword bags `reviewed` so the drafting script
never re-drafts them. All of this lives in `src/lib/eventIcons.ts`, which the
budget script **already forbids** from reaching the kiosk, so none of it touches
a lobby screen.

## Phase 7 — Drafting, review, and the switcher

1. `npm run translate` drafts both Chinese catalogues.
2. A bilingual reader works through `messages/GLOSSARY.md` first — the
   load-bearing terms, decided once — then the catalogues, flipping keys to
   `reviewed` as they go. Numbers' glossary is the model, including the pairs
   that differ by **vocabulary rather than script**: 登录/登入, 保存/儲存,
   加载中/載入中. A character-level conversion of zh-Hans is not zh-Hant and must
   never be shipped as one.
3. The language switcher lands in the account menu and on the sign-in screen.
4. `e2e/i18n.spec.ts` — one spec that exercises the Chinese catalogues. Every
   other spec stays pinned to `en` (`playwright.config.ts` gains
   `locale: 'en-US'`), which is what keeps the existing 834 assertions alive.
