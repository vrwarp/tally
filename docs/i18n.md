# Speaking three languages

Tally is used by a church whose families speak English, Mandarin and Cantonese.
The roster already carries their names in their own script — Planning Center
writes a child with a nickname as `Benson “蔡秉洲” Tsai`, and Tally has stored
that composite since the beginning. Every word around those names is English.

This document is the plan for changing that: **English, Simplified Chinese
(zh-Hans) and Traditional Chinese (zh-Hant)**, to the standard
[`vrwarp/numbers`](https://github.com/vrwarp/numbers) already holds — where a
missing translation is a red build rather than an English word on a Chinese
screen.

It is written to be executed in order. Each phase leaves the repo shippable.

---

## What we are copying, and what we are not

Numbers solved this once already, and the valuable part is not the library — it
is the **pipeline around the catalogue**: a record of which English each
translation was made from, a translator note per key, a drafting script that
respects human review, and a test that fails when English drifts ahead of the
Chinese. That machinery is framework-agnostic and ports almost verbatim.

The library does not port: Numbers is Next.js and resolves the locale on the
server. Tally is a static Vite SPA with two entry points and a Cloud Functions
backend.

The bridge is that **`next-intl` is a thin Next.js wrapper over `use-intl`**, by
the same author, with the same `useTranslations` API, the same ICU catalogue
format and the same typed-messages declaration. Tally takes `use-intl`
directly. Numbers' `scripts/translate-messages.ts`, `src/lib/translation-state.ts`
and `tests/unit/messages.test.ts` come across with the imports changed and
almost nothing else.

| Numbers | Tally | Ported? |
| --- | --- | --- |
| `next-intl` | `use-intl` | swapped |
| `src/i18n/request.ts` (cookie → `Accept-Language` → en) | `src/i18n/resolve.ts` (localStorage → `navigator.languages` → en) | rewritten, same shape |
| `messages/{en,zh-Hans,zh-Hant}.json` | same | same |
| `messages/translation-state.json` | same | verbatim |
| `messages/GLOSSARY.md` | same file, Tally's vocabulary | structure verbatim |
| `scripts/translate-messages.ts` | same | near-verbatim |
| `src/lib/translation-state.ts` | same | verbatim |
| `tests/unit/messages.test.ts` | `tests/messages.test.ts` | near-verbatim |
| `global.d.ts` typed messages | `src/types/messages.d.ts` | same idea |
| API errors → codes → `Errors.*` | `HttpsError` codes → `Errors.*` | same idea |

## The four rules

Lifted from Numbers' conventions, because they are what make the catalogue
survive contact with a second year of development.

1. **Every user-visible string comes from `messages/<locale>.json`.** Including
   placeholders, `title`, `aria-label`, toast text and confirm prompts.
   `en.json` is the only source of truth; the Chinese catalogues mirror its key
   set exactly.
2. **Whole sentences per key.** Never assembled from fragments. ICU plurals
   instead of `count === 1 ? 'name' : 'names'`. Each ternary branch is its own
   key. This is the rule that costs the most to follow and saves the most:
   Chinese has no verb agreement and different clause order, and a sentence
   stitched from three JSX children cannot be reordered by a translator.
3. **Every new key gets a `context` note.** Required for anything short or
   ambiguous — button labels, status chips, `Errors.*`. It is fed verbatim into
   the drafting prompt, so the translator never guesses at "Clock" or "Held".
4. **Never translate data.** Student and adult names, event titles a leader
   typed, label-template `{{tokens}}`, Material icon names
   (`local_fire_department`), grade values, backend ids.

## Phase 1 — Infrastructure

*Target: the loop works end-to-end on one screen. Nothing else changes.*

### 1.1 The locale module

`src/lib/locales.ts` — dependency-free and client-safe, imported by both entry
points and by the kiosk.

```ts
export const LOCALES = ['en', 'zh-Hans', 'zh-Hant'] as const;
export const DEFAULT_LOCALE: Locale = 'en';
export const LOCALE_LABELS = { en: 'English', 'zh-Hans': '简体中文', 'zh-Hant': '繁體中文' };
```

Script subtags rather than regions, for Numbers' reason: the Traditional-Chinese
audience spans Taiwan *and* Hong Kong. `negotiateLocale()` maps `zh-TW`,
`zh-HK`, `zh-MO` and `zh-Hant*` onto `zh-Hant`, every other `zh-*` onto
`zh-Hans`, and everything else onto English.

### 1.2 Resolution and persistence

Three storage tiers, because Tally has three kinds of reader:

| Reader | Where the choice lives | Why |
| --- | --- | --- |
| Counselor / core team | `users/{uid}.locale`, mirrored to `localStorage` | follows them to a new phone, like Numbers' `User.locale` |
| Signed-out visitor | `localStorage` only | there is no account to write to |
| Kiosk | `tally:kiosk:locale` in `localStorage` | the choice is a fact about *the tablet in this lobby*, not about a person |

`firestore.rules` currently lets a user touch exactly one field on their own
document:

```
allow update: if … (isSignedIn() && request.auth.uid == uid
                    && touchesOnly(['lastSeenAt']));
```

That becomes `touchesOnly(['lastSeenAt', 'locale'])`, with a rules test for both
the permitted write and the still-forbidden `role`/`active` escalation beside
it.

### 1.3 The provider

`IntlProvider` at both `createRoot` sites — `src/main.tsx` and
`src/kiosk/main.tsx`. The kiosk's is deliberately separate: it reads a different
storage key and a different catalogue slice (§4).

### 1.4 Typed keys

`src/types/messages.d.ts` declares `AppConfig['Messages'] = typeof en`, so a
typo'd `t('…')` fails `npm run build` rather than rendering a key path on a
screen. This is the single highest-value line in the whole plan.

### 1.5 The pipeline

Ported from Numbers:

- `src/lib/translationState.ts` — `flatten`/`unflatten`, `messageArguments`,
  and the two declared cross-key invariants (`SAME_VALUE_GROUPS`, `QUOTED_IN`).
- `scripts/translate-messages.ts` — drafts missing/stale keys in batches, pins
  `messages/GLOSSARY.md` into every prompt, validates that each draft preserves
  the English ICU arguments, and never overwrites a key a human marked
  `reviewed` without `--force`.
- `tests/messages.test.ts` — key parity, ICU-argument parity, no empty
  messages, both cross-key invariants in every locale, and source staleness.

One Tally-specific change: Numbers drafts through its own AI provider plumbing
(`src/lib/ai/providers`), which Tally has no equivalent of. Tally's script takes
an API key from the environment and is otherwise identical; `--todo` and
`--sync-state` work with no key at all, which is what CI and most contributors
need.

### 1.6 Test wrapper

90 test files import `render`/`renderHook` from `@testing-library/react`, each
behind its own local helper — 334 call sites. Rather than edit 334 helpers, add
`src/test/rtl.tsx`, which re-exports the whole of Testing Library with `render`
and `renderHook` wrapped in an `IntlProvider` pinned to `en`. A one-line codemod
rewrites the module specifier in all 90 files.

### 1.7 Proof

Extract one screen — Insights (`src/features/dashboard/DashboardPage.tsx`) — plus
the nav labels, run `npm run translate -- --todo`, then `npm test`.

**Done, and both gates were verified by deliberately breaking them:**

- Rewording `Dashboard.tileMia` in `en.json` from "MIA" to "Missing" turned the
  staleness test red, with both versions named in the failure:
  `translated from: "MIA" / en.json now: "Missing"`.
- Changing `Nav.insights` in `zh-Hant.json` turned the same-value test red:
  `Nav.insights must equal Dashboard.title (same UI element in two places)`.

45 keys, 3 catalogues, `translation-state.json` tracking all of them.

## Phase 2 — Extraction

*Target: `en.json` holds every user-visible string. Still English-only.*

**Done.** `messages/en.json` holds every user-visible string in the app and on
the kiosk, bar the carve-outs listed at the end of this section: **1,844 keys
across 68 namespaces**, 114 KB, of which the kiosk's slice is 12 KB. The suite
is green (190 files, 3,728 tests) and the kiosk's first paint is 118.7 KB gz
against its 127 KB budget.

`tests/messages.test.ts` also refuses a key nothing reads. A catalogue only
grows — a screen gets reworded and the key it used stays behind, and every
stale key is a sentence a translator is asked for that nobody will ever see.
The check is deliberately forgiving (a bare-name match anywhere in `src/`), so
the dynamic lookups this repo does on purpose still read as used.

Roughly **2,300 candidate strings across 109 files**. This is the long tail, and
it is safely interruptible: each screen is independent.

**The governing constraint is that extraction must be value-preserving.** Tally
has 1,162 unit-test text queries and 834 e2e ones against only 8
`data-testid`s. If every `en.json` value is byte-identical to the literal it
replaced, and tests run pinned to `en`, all 1,996 assertions keep passing
untouched. Deviating from the exact English is a separate, later commit.

Order, cheapest-risk first:

1. `src/components/ui` + `src/components` — shared chrome, ~70 strings.
2. `src/features/*` screen by screen — ~1,500 strings, the bulk.
3. `src/kiosk/*` — ~320 strings, under §4's constraints.
4. `src/lib`, `src/services`, `src/context`, `src/hooks` — ~410 strings, mostly
   error text and formatting helpers.

### One gotcha the first screen found

`useTranslations()` returns a new function identity per locale, so `t` has to
join the dependency array of every `useCallback`/`useMemo` that reads a string.
The Insights screen needed five. `react-hooks/exhaustive-deps` catches every one,
so it is noise rather than risk — but expect it on each screen, and add the dep
rather than silencing the rule.

### The sentence-assembly problem

~95 sites interleave prose with logic in a way English grammar leaks through:

```tsx
{listNames(held)} {held.length === 1 ? 'joins' : 'join'} this one:
`${list} ${names.length === 1 ? 'is' : 'are'} checked in. Welcome!`
{kin.length === 1 ? 'Another registration' : `${kin.length} other registrations`} in
```

Each becomes one key with an ICU plural:

```json
"heldJoin": "{count, plural, one {{names} joins this one:} other {{names} join this one:}}"
```

Chinese needs no plural branches — `other` alone is correct — which the drafting
prompt already states.

`joinNames()`'s `", "`/`" and "` becomes `Intl.ListFormat`, which gets `、` and
`和` right for free.

### Dates

8 bare `toLocale*` calls plus `date-fns format()` with hardcoded English
patterns (`'EEE, MMM d'`, `'h:mm a'`) across ~15 helpers in `src/lib/time.ts`.
A pattern string cannot produce `2月14日（週五）` or 上午/下午. These move to
`Intl.DateTimeFormat` via `useFormatter`, or to date-fns' `zhCN`/`zhTW`/`zhHK`
locale objects where the call site is not a component.

**Done, through `Intl`.** `lib/time.ts` takes a `TimeStrings` (a locale and the
four words `Intl` does not supply — Today, Tomorrow, Yesterday, "3 wks ago"),
and `useTimeFormats()` binds it for components so 121 call sites across 34 files
read `time.clock(…)` rather than growing an argument. `formatDistanceToNowStrict`
became `Intl.RelativeTimeFormat` on the same unit ladder. Nothing outside
`lib/csv.ts` and `lib/time.ts`'s `datetime-local` round-trip formats a date
through date-fns any more, and both of those are machine formats that must not
move with the locale.

Two English orderings changed with them, deliberately:

- **Birthdays** were the only day-first dates in the app (`'d MMMM'` — "14
  March"). Through `Intl` they read "March 14", which is what every other date
  on every other screen already did.
- **Name lists** gain the serial comma before "and", because no
  `Intl.ListFormat` style omits it and nothing hand-rolled produces 、 and 和.

### What the scanners could not see

Three classes of string survived a screen-by-screen pass looking extracted, and
each needed its own scan to find:

1. **Sentences JSX had broken in half.** A `>text<` match needs a text node with
   no expression inside it, so anything with a `{backendLabel}` or a
   `{student.firstName}` mid-clause was invisible. 21 of them, across 20 files —
   and they are the sentences most worth having whole, because the slot is
   exactly where a language moves.
2. **Strings holding the other quote character.** `"The child's first name"` is
   not matched by a literal scan whose character class excludes both quotes.
3. **Attribute values.** 25 `aria-label="Close"`, `label="Status"`,
   `title="Later"` — never JSX text, so never prose to any text scanner.

### Carve-outs — English on purpose

These are the strings `en.json` deliberately does not hold, and why:

- **`src/lib/registrationFields.ts`** — copied verbatim into the functions
  package and imports nothing. Its field labels become error codes in Phase 3;
  see "The shared-module carve-out" below.
- **`pcoErrorMarkdown` in `src/lib/pcoErrors.ts`** — a diagnostic somebody
  pastes to whoever administers the Planning Center account. `pcoKindKey` is
  already there for the half a person reads on screen.
- **The printer's event log** (`src/kiosk/printing/log.ts`, and the `noteId`
  written into it) — copied out for support, where a key that means the same
  thing in every language beats a sentence that changes with the kiosk's
  setting.
- **`src/lib/paths.ts`, `firebase.ts`, `firebaseConfig.ts`, `services.ts`** —
  deployment and configuration failures, addressed to whoever is holding the
  `.env`.
- **`useX must be used inside <XProvider>`** and the guard throws beside them —
  programming errors that reach a developer, never a counselor.
- **`'Untitled event'` in `src/services/converters.ts`** — the one genuinely
  user-visible holdout. It is a last-resort fallback for a document Tally's own
  editor cannot produce (the title is required), and it lives in a Firestore
  converter, which maps data and must not grow a translator to reach.
- **`LOCALE_LABELS` / `LOCALE_SHORT_LABELS` in `src/lib/locales.ts`** — a
  language's own name, which is the same in every catalogue by definition. The
  language switcher is read by somebody who cannot read the screen around it.
- **`src/lib/eventIconTerms.ts`** — the icon picker's Chinese search terms.
  A bag of words with pinyin in it, never displayed; Phase 6 §"Keywords are a
  search index" is the argument. The picker's *labels* are ordinary catalogue
  keys under `EventIcons.*`.

## Phase 3 — Server errors

*Target: the Cloud Functions stop speaking English at the user.*

72 `HttpsError` call sites in `functions/src` return prose that reaches the
screen verbatim. Numbers' answer is the one to copy: **the server emits a
machine-readable code; the client translates it.**

```ts
throw new HttpsError('permission-denied', 'Only an admin can do that.',
                     { code: 'auth.adminOnly' });
```

…resolved client-side by a `useCallableError()` hook against `Errors.*`, with
the raw English as the fallback for an unknown code. A code without a catalogue
entry fails the build, exactly as in Numbers.

### The shared-module carve-out

`src/lib/registrationFields.ts` is copied verbatim into the functions package by
`scripts/sync-functions-shared.mjs`, and it *imports nothing* — that is the price
of being shareable, and it is why its validation sentences are English literals
returned as data:

```ts
export type FieldCheck<T> = { ok: true; value: T } | { ok: false; error: string };
```

It cannot import an i18n runtime, and it must not. So `error: string` becomes
`code: ErrorCode` — a bare string union — and both callers (the kiosk's door
validator and the reviewer's form) translate at the edge. `tests/functionsShared.test.ts`
already fails on drift between the two copies, so this stays honest for free.

## Phase 4 — The kiosk

*Target: a lobby tablet speaks Chinese without breaking its byte budget or its
warm boot.*

`scripts/check-kiosk-budget.mjs` holds the tightest numbers in the repo: **250 kB
gzip** for everything reachable from `kiosk.html`, **130 kB** for the first-paint
subset. It already enforces two instances of one idea — *the kiosk is handed the
answers, not the code*:

- A gathering's theme is four hue names; `functions/src/kiosk/events.ts` runs the
  OKLCH gamut search and the chooser row carries **finished hex**.
- The icon catalogue is 60 kB of path data; the server looks one up and the row
  carries **one `iconPath`**.

i18n gets the same treatment, in three separate decisions.

**Pulled forward: the kiosk slice.** Phase 2's kiosk extraction needed a
catalogue on the lobby tablet, and the app's whole 85 KB `en.json` put first
paint 11 KB *over* budget on its own. So `scripts/sync-kiosk-messages.mjs`
already cuts the namespaces a lobby screen can reach into `messages/kiosk/`,
generated and committed with a drift test either way — a stale slice, or a
namespace the kiosk asks for that the slice does not carry, both fail the build
rather than rendering a key at a parent. §4.2 below is still to do, and is what
buys back the ~13 KB the ICU parser costs.

### 4.1 The other two languages — **done**

The budget script walks `.js` chunks: it reads the `assets/*.js` references out
of `dist/kiosk.html` and follows imports found in those chunks. A JSON
catalogue pulled with `fetch()` is **not in that graph at all**. A JSON
`import()` is — Vite compiles JSON to a JS module — and the plan took the free
one.

**It took the counted one instead, and paid for it.** A fetched asset is
*outside* the transform in §4.2, so it would arrive as ICU source with nothing
left in the kiosk that can read it — the compiled formatter hands a string
straight back, so `{count, plural, …}` would render as itself at a parent. An
`import()` goes through the plugin like everything else. The two are otherwise
the same file over the same wire: `public/kiosk-sw.js` caches `/assets/*`
cache-first either way, so an offline kiosk boots in its language either way.
What the fetch would have bought is 4.1 kB gz per locale of *accounting*, and
the price was a whole second compile path. Measured: **core 179.9 → 188.5 kB gz
against 244**.

So, in `src/kiosk/messages.ts`:

- **The `en` slice is bundled.** It is the default and the fallback, and
  something has to be renderable on the first frame.
- **The other two are imported lazily** and kept under `tally:kiosk:messages`,
  so a kiosk switched to Chinese paints Chinese on the *first frame* of every
  boot after the first — the same move `KIOSK_KEYS.roster` and `participation`
  already make, for the same reason: the lobby screen has to work before the
  network answers.

The stored copy carries the **shape** of the English slice it was written
against — the key tree with the messages thrown away — and is discarded when
that no longer matches the build. A reworded message is worth one boot of
staleness; a key added by a deploy is `Register.labelFirstName` on the glass in
front of a parent, and only the second is worth throwing a warm start away
over. The refreshing import starts on the same frame regardless.

### 4.2 The ICU runtime — precompile, don't ship a parser — **done**

**Measured in Phase 1: `use-intl` + `intl-messageformat` costs 15.2 kB gzip**
(total dist JS went 522.7 → 537.9 kB gz when the provider landed in the main
app). That is the one genuine cost, and it is charged whether the import is
static or dynamic.

The answer is to **compile messages at build time**, and the mechanism was
already in the installed package rather than something to build:
`use-intl/format-message/format-only` formats messages precompiled by
`icu-minify`, and that module **imports nothing at all** (1.9 kB minified, no
`intl-messageformat`). The core reaches its formatter through the bare specifier
`use-intl/format-message`, so swapping it is a resolve alias rather than a code
change — no component knows which formatter it got.

**Not scoped to the kiosk, in the end, because it cannot be.** Both entries
share one build and therefore one `use-intl`; a per-entry alias would need the
core compiled twice. The choice was to ship the parser to everyone or to no
one, and shipping it to no one is both simpler and the better trade — the main
app's grammar is as knowable at build time as the kiosk's. So:

- `scripts/vite-compile-messages.ts` compiles every message in `messages/` as
  Vite reads it. It is a *transform*: the catalogues on disk stay plain ICU,
  which is what the pipeline, the parity tests and a human reviewer read.
  Nothing is generated into the repo.
- `vite.config.ts` aliases `use-intl/format-message` to `format-only`, anchored
  so the replacement's own specifier is not rewritten.

Measured: **kiosk first paint 118.7 → 110.3 kB gz**, core 188.4 → 179.9, and
`intl-messageformat` is absent from `dist/` entirely — the main app stops
paying for it too.

Two consequences, both written down where they bite:

- **`t.raw()` throws** under the compiled formatter — there is no source string
  left to hand back. Nothing uses it; `tests/compiledMessages.test.ts` fails if
  something starts to.
- **Vitest loads neither half**, so the unit suite renders components against
  the ordinary parser — which is right for a test that is about a screen, and
  leaves exactly one gap. `tests/compiledMessages.test.ts` is that gap: it
  compiles every message in every catalogue and formats it through
  `format-only` with values invented from the compiled shape (a number for a
  plural, a `Date` for a date, a function for a tag), three times over for a
  plural because a compiled plural is a table.

That test earned its keep on the first run: `LabelTemplate.bracketsHint` read
`<example>{example}</example>` — the same name as a tag and as an argument,
which no set of values can satisfy — while its call site passed a `code`
function for a tag the message did not have. It had been rendering its own key
since extraction. One name cannot be both, and now nothing can ship that way.

### 4.3 What the server should render — **declined, with the reason**

The proposal was for the chooser row to carry a pre-formatted, localized date
and time alongside its resolved palette and icon, deleting the kiosk's
date-formatting path as a bonus.

It does not pay here, and the reason is that the premise is wrong: the palette
and the icon are *libraries* — 60 kB of path data, a gamut search — while
`Intl.DateTimeFormat` is a browser API that costs nothing to call and nothing
to ship. There is no code to delete, only a place to move it to. Moving it
would buy a locale round-trip: the kiosk's language is a setting on the glass,
so a row formatted by the server is stale from the moment somebody presses a
chip until the next poll answers — and the switcher in §4.5 makes that a
gesture a parent performs, not a deploy.

The section's *other* half stands and is why it is kept: the kiosk's UI strings
are not the server's to send. They are static chrome, the lobby screen must
paint before a callable answers, and routing them through `getKioskEvents`
would turn every copy edit into a functions deploy.

What the review did find is that the kiosk was formatting dates against the
**browser's** language rather than its own — `Intl`'s default is the device, and
the kiosk's is a setting. A tablet sold in English, set to Chinese, showed a
Chinese title over English opening hours. Fixed by passing the locale where the
words are already passed: `eventWindow`, `opensAtLabel`, the chooser rows, the
printer log, and the two `{{date}}`/`{{time}}` tokens on a printed label, whose
language is the language of the room. Three of the same in the main app
(`PastGatherings`, `ImportCheckInsModal`, `KioskBackdropField`) went with them —
everything else there already went through `useTimeFormats`, which has been
locale-aware since Phase 2.

### 4.4 A fourth budget assertion — **done**

`ICU_PARSER` in `scripts/check-kiosk-budget.mjs`, beside `OKLAB_MATRIX` and
`ICON_CATALOGUE` and for the same money. Both halves of §4.2 are one line each,
and losing either brings the parser back for the whole build rather than for one
screen — an alias that stops matching after a `use-intl` upgrade, a `messages/`
path the plugin's regexp no longer recognises, or somebody reaching for
`intl-messageformat` directly to format one date. The bytes would land in a
shared chunk well inside the headroom and nothing else would notice.

Matched on `The intl string context variable` and `EXPECT_ARGUMENT_CLOSING_BRACE`
— literals from the formatter and from its parser, which can arrive separately,
and which a minifier cannot rename. Verified by removing the alias and rebuilding:
the guard names the chunk and fails the build.

### 4.4b Names at the door say which language

The registration wizard asks a parent to type two names per child and two more
for themselves, and the keyboard under those questions is the fixed QWERTY
described in Phase 5 — no IME, because the kiosk never focuses a focusable
element. So a Chinese name is not merely awkward to enter there, it is
unenterable, and a question reading 名字 over keys that cannot produce one is a
dead end with no sign on it.

The wording is the fix. The Chinese questions ask for the **English** name —
英文名字, 英文姓氏 — which is exactly what the keys below them make, so the
constraint and its answer are the same sentence. English needs no such warning
and does not get one; this is a deliberate divergence between the locales, and
`REQUIRED_WORDING` in `src/lib/translationState.ts` is where it is declared so
it survives a re-draft. The parity test enforces it once a translation exists,
and the drafting script carries it as a `mustContain` — which rejects a draft
that drops it rather than shipping one.

Nothing about the roster changes. `searchName` still holds the composite
(`Benson “蔡秉洲”`), a leader can still type the Chinese into the app on a real
keyboard, and Phase 5's pinyin index is what makes that row findable *from* the
kiosk. This is only about what the lobby's own keys can write.

### 4.5 Language on the glass — **done**

`src/kiosk/components/LanguagePicker.tsx`, in two weights.

**Setup, on the pairing screen.** A kiosk is bolted to a wall and configured
once, and that screen is the single moment a member of staff is standing at the
device with a decision to make about it. Set before pairing, so the first
screen a parent ever meets is already in the room's language;
`KIOSK_LOCALE_STORAGE_KEY` survives pairing, unpairing and the ~4am reload
alike.

**Standing, on the search screen**, in the readout band — quiet weight, one
glyph per language. Not the header: header height comes out of a results track
already under three hundred pixels on the landscape kiosk. The band is
fixed-height and already `relative` with the match count absolutely placed in
its right corner, so the picker takes the left one and costs no geometry at all
— which is the promise that file makes about keystrokes. Both corners now
inset the centred buffer, which fixes a long name being centred *through* the
count as a side effect.

Not a modal, per the plan: a parent who realises mid-search that they cannot
read the screen presses a chip and the words change under them, with their
place in the queue untouched.

The languages wear their own names (`LOCALE_LABELS`, never translated) because
the reader who needs this control is by definition not reading the words around
it. Persistence is the *provider's*, not the picker's — the kiosk writes
against the tablet, the app against the reader — which is what lets Phase 7's
account-menu switcher be the same component.

Found on the way: `{matchCount} names` in `SearchScreen` was still assembled in
English, plural and all. It is `Search.matchCount` now, a real ICU plural.

## Phase 5 — Names in Chinese: pinyin search — **done**

*Target: a parent types `caibingzhou` and finds 蔡秉洲.*

The kiosk keyboard is one static QWERTY layout, and the kiosk **never focuses a
focusable element** — that is what lets it avoid the device's slow native
keyboard. So there is no IME, and a Chinese name is unreachable by typing it.
Pinyin is the answer, and it was nearly free because of how search already
works.

`searchName` is a **stored, denormalized field**, and the kiosk only ever asks
`haystack.includes(needle)` of it. So: **widen the haystack, not the kiosk.**

```
蔡秉洲  →  "蔡秉洲 caibingzhou cbz tsaibingzhou choibingzhou tbz chuabingzhou"
```

Full syllables *and* initials, so both `caibing` and `cbz` land. **No matcher
change at all**: `normalizeForSearch` already lowercases and folds diacritics,
and `compact()` already strips word gaps.

`functions/src/names/pinyin.ts` is the module. `pinyin-pro` rather than
`tiny-pinyin`: it reads Traditional as well as Simplified, which a church with
Taiwanese and Hong Kong families is not optional about, and it can be asked for
*every* reading of a character rather than its best guess.

### Ambiguity is additive, never a choice

The plan expected a hand-curated table to adjudicate the heteronym surnames a
roster is full of — 單 is *shàn* and not *dān*, 曾 is *zēng*, 查 is *zhā*. There
is nothing to adjudicate: this is a search index, not a transcription, so every
reading goes in. A token that finds nobody costs a few bytes; a family whose
surname was read the other way finds nobody at all.

That left the table free for the job worth a human's attention, which turned out
to be a different one: **the other alphabet a Chinese surname is written in.**
蔡 is Tsai and Choi as often as it is Cai here, and a parent types the spelling
on their ID card. `SURNAME_SPELLINGS` is the Cantonese and Wade-Giles table,
Traditional and Simplified listed separately because they are different
characters, applied only to the first character of the name — which is where a
Chinese surname is. It matters most for the Attendees-32 rows, whose names are
CJK with no Latin half to fall back on.

The ü gets both spellings: `normalizeForSearch` folds `lü` onto `lu` (the
passport), and `lv` (the keyboard) goes in as a token. The matcher's own
`umlautVariants` already handles the query side, so neither has to be right
alone.

### Where it runs

Server-side, and nowhere else — the dictionary is close to a megabyte. It is
deliberately **not** part of `buildSearchName`, which lives in the module set
`scripts/sync-functions-shared.mjs` copies into the functions package precisely
because those modules import nothing; a dictionary inside one would ship it to
the client *and* the kiosk. So `withPinyin` post-processes what that function
builds:

- Every server write path calls it — both mappers, kiosk registration, amend.
- `onStudentNamed` (`onDocumentWritten` on `students/{id}`) catches what the
  client writes for itself from a phone. It cannot loop by construction rather
  than by a guard: it fires on its own write and `withPinyin` is idempotent.
- `npm run pinyin:backfill` (dry by default, `-- --apply` to write) catches up
  the roster nothing has touched since. It leaves `updatedAt`/`updatedBy` alone:
  nothing about the student has been edited, and stamping four hundred rows as
  edited today would bury every real edit in the screens that sort by it.

No budget guard was needed. `pinyin-pro` is a dependency of the functions
package alone, so an import from `src/` does not merely cost bytes — it fails
the build.

### Sorting

`Intl.Collator` cannot do this: given Hanzi it clumps them all together, before
the Latin names under a `zh` collation and after them under an `en` one, and
neither is a list a counselor can scan. 蔡秉洲 belongs between Bergman and Chen.

Filing them there means romanizing, and romanizing is the thing that must not
reach the client — so the client reads back what the server already wrote.
`nameSortKey` in `src/lib/utils.ts` takes the token immediately after the
Chinese in `searchName`, and `withPinyin` writes the canonical reading in
exactly that position. **The token order is a contract between the two**, which
is why the alternatives are sorted after it rather than the whole list being
sorted. A row nothing has widened yet falls back to the name itself, which is
where it already was.

## Phase 6 — The icon picker — **done**

*Target: the event icon picker is searchable in Chinese.*

`searchEventIcons` matched a query against
`` `${label} ${name.replace(/_/g,' ')} ${keywords}` ``, over 114 icons. The two
halves of that haystack needed opposite treatment, and they got it.

**Labels are ordinary UI strings**, so they are ordinary catalogue keys:
`EventIcons.<name>`, 114 of them, each with a `context` note naming the glyph,
what it depicts and the width it has to fit. They are one or two words and
genuinely ambiguous — "Clock", "Groups", "Today" — which is what rule 3 is for.
`EventIconDef.label` keeps the English, and a test pins the two to each other:
the same drift guard `FIELD_MESSAGES` has.

**Keywords are a search index, not prose**, so they are *not* in the
catalogue at all. `src/lib/eventIconTerms.ts` holds them as data. The plan put
them in `messages/` marked `reviewed` so the drafting script would leave them
alone — but "in the queue, flagged not to be worked on" is a weaker version of
"not in the queue": a bag of words has no sentence to get right and no register
to match, and every extra term is a small win rather than a risk. Nothing there
is ever displayed, which is the line rule 1 actually draws.

**One bag for both Chinese catalogues**, and that is not the shortcut it looks
like. Simplified and Traditional are genuinely different vocabularies — the
reason `zh-Hant` is hand-maintained and never a character conversion — but this
is an index: 營 and 营 both go in both times, and the union is strictly better at
the one job the data has.

**Pinyin, generated once and kept by hand**, so 露營 is reachable by typing
`luying` and a leader searching in Chinese does not have to switch IME in the
middle of a form. Produced from Phase 5's romanizer rather than at build time —
a generator step, a committed artefact and a drift test would be three moving
parts to keep a static table current, and the table has the same standing as the
path data beside it: generated once, then kept by hand.

The haystack is `label(reader) + label(en) + name + en.keywords + zh terms`,
and every part earns its place. The **English half stays unconditionally**, so
nothing gets worse than it was and a leader who learned "camp" from five years
of Tally still types it. The **Chinese half is in for everybody** rather than
only for a Chinese reader: an English screen costs nothing to search in Chinese,
and the branch that would save those bytes is a branch that can be wrong. The
**Material name is never translated and never dropped** — it is the paste path,
and somebody arriving with `local_fire_department` from Google's own docs has to
land on the icon it names.

**Where it lives moved.** `searchEventIcons` is now
`src/lib/eventIconSearch.ts`, because `eventIcons.ts` is copied verbatim into
the functions package by `scripts/sync-functions-shared.mjs` and every module in
that set must import nothing — the server looks an icon up by name for a kiosk
chooser row and has never searched anything. The catalogue stays shared and
import-free; the searching sits where only the app can reach it. The kiosk is
already forbidden from reaching either by the budget script's `ICON_CATALOGUE`
guard, so none of this touches a lobby screen.

Found on the way: `Icon`, `Done` and `Change` in `IconPickerField` were still
hardcoded English. They are `Events.iconLabel`, `iconDone` and `iconChange` now.

## Phase 7 — Drafting, review, and the switcher

1. **`npm run translate` drafts both Chinese catalogues.** Not run yet: it is
   the one step here that needs `ANTHROPIC_API_KEY`, and the machine this was
   built on has none. Everything the run needs is in place — a `context` note on
   every key added since Phase 2, the glossary, `REQUIRED_WORDING`, and the
   `mustContain` gate that rejects a draft dropping 英文 — and the catalogues sit
   in their correct pre-draft state: every key present, holding the English
   verbatim, every status `todo`. The parity test is green because of that, and
   a screen switched to Chinese today reads English rather than keys.
2. **A bilingual reader works through `messages/GLOSSARY.md` first**, then the
   catalogues, flipping keys to `reviewed` as they go. This is a human's step by
   construction: nothing else in the pipeline can tell a right translation from
   a plausible one.
3. **The switcher lands in the account menu and on the sign-in screen** —
   `src/components/LanguageChoice.tsx`. The sign-in screen is the one that
   matters most: everywhere else the control is behind a sign-in, so a counselor
   who cannot read *that* page has no way to reach the thing that would fix it.
   In the account menu it is deliberately **not** a `menuitem` — every other row
   there is a destination, and this changes the words and leaves the reader
   where they are, which is also why the menu stays open afterwards.
4. **`e2e/i18n.spec.ts`**, with `locale: 'en-US'` pinned in
   `playwright.config.ts` for every other spec — the app negotiates from
   `navigator.languages` when nobody has chosen, so a runner whose image is set
   to Chinese would otherwise put the whole suite in an unreviewed catalogue and
   fail eight hundred assertions written against the English wording.

   The spec deliberately asserts no Chinese wording. Drafts are machine output
   until a reviewer has seen them, and a spec that pinned a sentence would go red
   the first time somebody improved one. It asserts the machinery instead, which
   is what actually breaks: the locale chunk resolves, the choice survives a
   reload, the kiosk's language stays apart from the app's across the same
   browser, and **no message key reaches a screen** — the failure a catalogue
   parity test structurally cannot see, since it compares catalogues rather than
   what was rendered.

**`<html lang>` follows the locale**, added here because the spec wanted a
locale-independent assertion and it turns out to be the right thing anyway: it
is what a screen reader picks a voice from, what a browser hyphenates by, and
what "translate this page" offers to do. `index.html` and `kiosk.html` ship
`lang="en"` because something must be there before React runs; both providers
correct it.

**Left undone, and named rather than quietly skipped.** `reconcileLocale` in
`src/i18n/localeStore.ts` — the sign-in reconciliation that would make a
language choice follow a counselor to a new phone — is still unwired. It needs a
`locale` field on `users/{uid}`, which means a converter change and a
`firestore.rules` change to the one self-write a person is allowed
(`touchesOnly(['lastSeenAt'])`). That is a schema and security change the plan
did not ask for, and the rules suite is how it would be proved. Until then the
choice lives in `localStorage`, which is where the app reads it from on every
boot anyway.
